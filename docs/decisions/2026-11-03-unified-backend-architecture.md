# MontClip 自动化 / 精细化两种界面 + 统一后台：架构草案（Deja，v0）

状态：草案，等 DD 功能清单、VV 界面方案、JJ 需求回来后改成 ADR，放进仓库 docs/decisions/。

## 主人的要求（原话要点）
1. 自动化界面做得和 hotclip 一样好，最好更好。
2. hotclip 和 MontClip 的功能都拆成小块，统一放进以 MontClip 为底座的后台。
3. 自动化界面里的全自动工作流，等于精细化界面里一串半自动工作流组合起来。
4. 不管在哪个界面，都能用自然语言让 AI 调用 MontClip 来剪辑和生成视频。

## 主人 11-03 追加的硬规则
- HotClip 带弹幕找高光的方法，先照它的思路做，以后再微调。走 clean-room：Rea 读源码，写行为规格 SPEC；实现方只看 SPEC。
- HotClip 的每个功能，在 MontClip 里实现时，必须拆成底座精细化界面里能交互、能单独用的剪辑/生成能力（op/step）的组合。
- 底座没有对应能力，就先在底座上把这个能力补上，再拿来组成自动流程。
- 不允许出现只在自动化流程里才有、精细化界面里用不了的「黑盒」功能。
- 验收方法：每个自动化工作流都附一张表，列出它由哪些底座能力组成；表里每一项，在精细化界面里都能单独点到，也能用自然语言单独调用。

## 边界
- hotclip 是 AGPL-3.0，MontClip 是 MIT。只学它做了什么、用户怎么操作，不复制代码、文案原句和美术资源。学习材料只写行为，不写代码。参照「只看不照抄」那条约定，记进 ADR。
- 之前定的规矩继续有效：
  - 不用 Python，后台只用 JS/Node，加上 ffmpeg。
  - 默认不联网。会联网的只有联网例外清单里的几项：AI 助手、下载听写模型、主播自己打开的云端听写、按歌词查歌名。主人指定的云模型（OpenRouter DeepSeek Flash 看画面）也要明确提示用户。
  - 一个项目只有一条修改记录和一条撤销链。
  - 预览和导出共用同一个合成器。

## 三层结构
1. **操作（op）**：最小的、能单独测试的一步。每个 op 有固定的输入输出格式，做的事只落到项目修改记录上，能撤销。
   例子：导入素材、读弹幕、算音量曲线、听写、找高光候选、按句选段、裁成竖屏、加字幕、起标题、导出 MP4/SRT/映射。
2. **步骤（step）**：精细化界面里主播点一次按钮做的事，通常是一个或几个 op，再加一次「看一下、确认」。
   例子：「找高光」这一步 = 算音量 + 读弹幕 + 打分，结果显示成候选卡，主播勾选。
3. **工作流（workflow）**：一串 step 加上默认选项。
   - 自动化界面跑工作流时，每个 step 的「确认」用默认值自动通过。
   - 跑到任何一步都能停下，切到精细化界面，从这一步接着手动做。
   - 工作流本身是一份可读的配置（JSON），不是写死在代码里的流程。

## 自然语言（AI）
- AI 能调用的工具，就是上面的 op 和 step，界面按钮背后也是这一套，不另做一套 AI 专用接口。
- 现有的剪辑聊天沿用「提案 → 预览 → 应用 → 撤销」。AI 的每次修改都是项目修改记录里的一步，可以撤销。
- 同一套工具用 MCP 对外开放，现有 mcp-server 扩展到所有 op。

## 先做什么（等三份调研回来后细化）
1. 先给现有功能编 op 清单，不加新功能，只把已有按钮背后的动作整理成统一的 op 接口，测试全部过。
2. 定工作流配置格式，做出第一条工作流：「直播录像 → 高光候选 → 自动选前 N 条 → 竖屏 → 字幕 → 导出」。
3. 做自动化界面（照 VV 方案）。
4. 补 hotclip 有、我们缺、JJ 标「必须有」的功能，每个功能做成一个新 op。
5. 高光算法：先补上新信号（看画面、说话内容、直播时的弹幕），再调优。

## AI 拆任务、排计划、执行（主人 11-03：参考 Codex CLI）
参考对象：OpenAI Codex CLI（Apache-2.0，可以读源码，也可以借用）。它的做法：
- 有一个 `update_plan` 清单工具。每一步写成 {step, status}，状态只有 pending / in_progress / completed 三种，同一时间只有一步处于 in_progress。
- 模型一边调工具一边更新清单，用户在界面上实时看到计划和进度。
- 另有「计划模式」：只读、只出计划，用户点了同意才开始执行。
- 有危险的动作走审批策略。

MontClip 的对应设计：
1. **能力表**（相当于编程语言里的「指令集」）：每个底座能力登记以下内容：
   - 名字、输入输出的 JSON schema、一句白话说明；
   - 副作用等级：只读分析 / 改项目 / 导出写文件 / 联网；
   - 预计耗时。
   AI 只能调用能力表里的能力。界面按钮调的也是同一张表。
2. **计划（plan）**：AI 先把一句话拆成有序的若干步，每一步对应一个能力调用，后一步可以引用前一步的输出（例如「第 1 步找出的歌」）。计划在聊天面板里显示成清单，每一步的状态实时更新。
3. **执行规则**：
   - 只读分析的步骤（找歌、找高光、听写）直接执行；
   - 改项目的步骤先出预览，主播点「应用」后才写入，并且算作修改记录里的一步，可以撤销；
   - 导出和联网的步骤，执行前必须问主播；
   - 执行之前主播可以改计划：删掉某一步、改某个参数，或者整个不要。
4. **配方**：一份跑通的计划可以存成「配方」。自动化界面的一键流程，其实就是运行一份内置配方。配方里每一步都在精细化界面里有对应的按钮，所以「全自动 = 多个半自动步骤串起来」在实现上是同一件事。
5. **校验**：模型的输出一律只当数据看，不当程序执行。每一步的参数都要先按 schema 和项目状态校验（时间不越界、素材存在、区间不重叠），通过了才执行。计划最多 30 步；某一步出错就停在这一步，把原因告诉主播。
6. **模型要求**：需要支持工具调用（function calling）。DeepSeek flash 支持。不配 AI 时，本机只用固定规则从配方里挑一份来跑。
7. **落地顺序**：
   - keep_ranges 和 per_range（正在做）；
   - 能力表，以及把现有的 MCP 工具登记进去；
   - plan 清单面板，加上 update_plan；
   - 把「找出每首歌」「找高光」登记成能力；
   - 配方的存储和运行，接到自动化界面。

## 总定位：视频剪辑里的 Cursor（主人 11-03）
主人原话：「MontClip 应该变成视频剪辑工具中的 Cursor」。
Cursor 的做法是：编辑器还是主体，人照样自己写代码，AI 贴在每一个动作旁边。对到 MontClip：

| Cursor | MontClip |
|---|---|
| 编辑器是主界面，人能自己改每一行 | 剪辑器（时间线 + 预览）是主界面，主播能自己调到每一帧 |
| Agent 面板：一句话 → 计划 → 调工具 → 看改动 → 接受或拒绝 | AI 聊天面板：一句话 → 计划清单 → 调用底座能力 → 预览 → 应用或撤销 |
| Cmd+K：选中一段代码，直接说怎么改 | 选中时间线上的一段或一张卡，直接说「开头往前 2 秒」「做成竖屏」 |
| Tab 补全：猜你下一步要做什么，按 Tab 接受 | 下一步建议：调完一首歌，提示「后面 6 首也按这个对齐？」，按一下接受 |
| @ 引用文件、符号、文档 | @ 引用某段素材、某首歌、某句字幕、某张高光卡 |
| diff 显示改了什么，可以逐条接受 | 时间线上显示改动前后的对比，可以逐段应用或撤销 |
| checkpoint，随时回到之前的状态 | 项目修改记录和撤销链，AI 的每一步都是一个可以回退的点 |
| .cursorrules 记住项目的规矩 | 主播的剪辑习惯：结尾多留几秒、默认不带弹幕、字幕放哪 |
| 权限模式 | 计划 / 手动 / 自动 / Yolo |
| 可以换模型 | 可以换模型（DeepSeek flash 等），也可以不配 AI，只用本机规则 |

由此得出几条原则：
1. 主界面永远是剪辑器。AI 和自动出切片都是贴在旁边的助手，或者弹出来的一步（和主人说的「自动化只能是弹出的某一步」一致）。
2. AI 做的每一件事，主播都能自己手动做到；手动能做的每一件事，AI 也能调用。两边用同一张能力表。
3. AI 改了什么，一定要让主播看得见，并且能撤销。
4. 要给 AI 上下文：选中了什么、@ 了什么、项目现状和剪辑习惯。但不把录像、画面或声音发出去，除非这一项在联网例外清单里。

## AI 的权限模式（主人 11-03：参考 Codex / Cindy）
主人原话要点：
- 权限分四种交互模式：计划、手动、自动、Yolo。
- 手动模式下，第一次出现的工具操作，如果不在黑白名单上，就问用户：只批准这次 / 这个聊天中都批准 / 不同意。
- 自动模式下，只在黑名单、敏感或无法撤回的操作上问。

每个能力在能力表里都标一个风险等级：
- **只读**：找歌、找高光、听写（本机）、读项目。
- **可撤销**：选段、裁剪、加字幕、改字幕。这些都记在项目的修改记录里，可以撤销。
- **敏感 / 撤不回**：导出写文件、覆盖文件、删文件（包括删副本）、任何把数据发出去的操作（云端听写、按歌词查歌名、AI 助手请求）。

四种模式下 AI 怎么做：

| 模式 | 只读 | 可撤销 | 敏感 / 撤不回 | 黑名单 |
|---|---|---|---|---|
| 计划 | 可以做 | 不执行，只列进计划 | 不执行 | 不执行 |
| 手动 | 白名单里的直接做；第一次碰到不在名单上的，问三选一 | 第一次问三选一 | 每次都问三选一 | 拒绝 |
| 自动 | 直接做 | 直接做（可以撤销） | 问三选一 | 拒绝 |
| Yolo | 直接做 | 直接做 | 直接做；联网发送仍需主播已经在设置里打开对应功能，域名也必须在白名单里 | 拒绝 |

- 「这个聊天中都批准」只对同一个能力、同一个目标（同一个域名，或同一个导出文件夹）有效，换了聊天就失效。
- 黑名单写死在程序里，任何模式都不能放开：删除或改写原始录像；发到白名单以外的域名；读写工作区以外的文件。白名单和用户自己加的黑名单可以在设置里改。
- 按歌词查歌名属于「敏感」：手动模式和自动模式下，发送前都要弹三选一。弹窗里列出这次要发的几句歌词，以及发给哪个域名。
- 默认模式是「手动」。模式选择在聊天面板顶部，跟 Cindy 的位置一样。

## 对 VV 原型 v1 的后台承诺（11-03）
- 「找高光」「找出每首歌」按段计算，每段的结果都存进项目。主播点了「停下」，下次从没算完的那段接着算，已经算出的结果不丢。
- 没配 AI 时，本机只听懂固定的几类说法：条数、时长、画幅、只要唱歌 / 不要聊天、整首 / 副歌。其他说法提示主播要先配 AI。
- 歌名本机拿不到，默认写「第 N 首 · 时间」，主播可以改名。配了 AI 以后可以根据歌词猜歌名。
- 每段都附一个把握程度。把握低的段，界面上标出「开头可能不准」。
- 同时导入多场录像时，结果按场分组显示。
- 换了「这场主要在干什么」后重新挑：主播勾过或调过开头结尾的片段锁住不动，只重挑没碰过的。
- 找完时如果窗口不在前台，发一条 Windows 本机系统通知。
- 「加字幕」这一步可以一键设置所有字幕：字号大 / 中 / 小，位置上 / 下。导出页不重复放这个设置。

## 权限模式：QQ 安全审查后的修订（11-03，以本节为准）
QQ 审查意见：QQ workspace 的 documents/2026-11-03-MontClip-AI权限模式-安全审查-QQ.md。以下 8 条 Deja 全部采纳：
1. 「外发」单列一类，和「敏感」分开。任何模式下（包括 Yolo），外发前都要显示这次要发的内容和目标域名，并且可以取消。「这个聊天中都批准」只是免掉再点一次「同意」，内容照样显示。具体是每次都提示，还是一个聊天里只提示一次，等主人拍板；拍板前按每次都提示做。
2. 风险等级写死在主进程里，页面和 AI 都改不了。目标（origin、realpath）由宿主做规范化后再比对。批准只存在内存里，重启后清空。
3. AI 不能修改：权限模式、黑白名单、联网开关。切到 Yolo 要主播自己主动确认；Yolo 期间界面上一直有标识；重启后回到手动。
4. 审批框只由宿主弹出。弹幕、字幕、AI 回复里出现的「同意」一律不算数。
5. 「覆盖已有文件」放进黑名单。
6. 导出写文件只能走系统保存窗口，AI 不能自己指定路径。
7. 自动模式下改项目，要用 revision 做 CAS（项目在这期间被改过，就拒绝执行），而且每一步都能撤销。
8. 外发有上限（每次的字数或字节、每个聊天的总量），Yolo 下也照样生效。
9. 「都批准」只在当前这一次会话里有效：在助手里，指这一段聊天；在弹出的流程里（如「✨ 自动出切片」），指这一次流程，从打开到找完或关闭为止。换一场录像、重新跑一次流程、或者重启软件，都要重新批准。按钮文字按场景来写，例如〔这次找高光都批准〕。
10. 自定义的云端地址要过两道关：第一道是「信任这个地址」，属于设置，确认框里显示完整域名，只接受 https；第二道是每次实际发送前的三选一，照常显示要发的内容和发往的地方。
11. **主人拍板（2026-11-03）**：「往外发数据时，每次发送前都显示要发的内容和目标网站，选了『这个聊天中都批准』也照样显示，只是不用再点同意。」以后都按这条执行，第 1 条里待定的部分以此为准。

## 每一步都是编辑器事件（主人 11-03）
主人原话：「每一步都要拆解成事件，对应到编辑器的事件中去，这样就可以让 AI 在该停下询问的时候询问，可撤回编辑，也可以全自动一直到出结果。」

现有的底子（main 上已经有）：
- edit-ops.js：编辑器快捷键和 MCP 里 agent 的 patch 用的是同一份代码。
- 编辑器外面包了撤销栈；history.js 保存版本。版本分 manual、auto、agent、restore 四种，而且永不覆盖、永不丢。

做法：
1. **统一事件格式**：任何一步，不管是主播点按钮、AI 调能力，还是配方自动跑，都产生同一种事件：
   `{id, runId, step, capability, args, actor: 主播|AI|配方, risk, state, revisionBefore, revisionAfter, at}`
2. **事件状态**：
   - 规划中 → 等确认 → 执行中 → 有结果（预览）→ 已应用 / 被拒绝 / 已撤销 / 失败；
   - 只读的能力：执行中 → 有结果；
   - 改项目的能力：有结果后要先「应用」，才会产生 revisionAfter；
   - 外发和撤不回的能力：执行前一定先进「等确认」，显示要发的内容和发给谁。
3. **停下还是继续，由事件状态和权限模式决定**：计划清单里每一步都对应一个事件。轮到这一步时，宿主（不是 AI）按「风险等级 × 当前权限模式」判断：
   - 直接执行；
   - 停在「等确认」，弹三选一；
   - 拒绝。
   - 全自动：每一步的确认都按允许规则自动通过，一路跑到导出。中途哪一步失败了，就停在那一步。
4. **撤销以事件为单位**：每个「已应用」的事件就是撤销栈里的一项，它的 revisionBefore 就是撤销后回到的状态。AI 连续做了五步，可以一步一步撤，也可以按 runId 一次把这五步全部撤掉。宿主在 AI 开始之前先存一个 agent 版本，最坏情况下可以整体恢复。
5. **主播和 AI 走同一条路**：主播在界面上手动做的操作，也写成同样的事件，标 actor=主播。所以 AI 能看到主播刚改了什么（相当于 Cursor 的上下文），「下一步建议」也从这里来。主播动过的东西，AI 在执行时会把它当成锁住（CAS：revision 对不上就停下来问）。
6. **事件日志**：
   - 保存在项目里，每个事件只记参数和结果的摘要，不存录像、画面和声音；
   - 外发事件要记下「发了什么、发给谁、多少字节」，主播可以在项目里查到；
   - 事件日志就是「配方」的来源：一次跑通的 run，可以存成配方。
7. **示例：唱歌一首一个切片，加歌词校准**
   - ① 找出每首歌（只读）
   - ② 查歌名（外发，等确认，显示要发的两三句和网址）
   - ③ 收到歌名和歌词（结果）
   - ④ 按歌词校准字幕（改项目，出预览，逐行应用）
   - ⑤ 每首做成一个切片（改项目）
   - ⑥ 导出（撤不回，用系统保存窗口）
   在手动模式下，会在 ②、④、⑤、⑥ 停下；在 Yolo 模式下，只有 ② 会显示要发的内容（可以取消，不用点同意），⑥ 会弹出系统保存窗口，其余直接跑完。
12. 「都批准」按钮按所在场景来写：
    - 弹窗流程里，写〔这次找高光都批准〕，到这次流程结束为止有效；
    - 主界面的编辑操作（文稿面板、片段右键菜单、细剪的字幕页），写〔这个项目这次都批准〕，到切换项目或关掉软件为止有效；
    - AI 聊天里，写〔这个聊天中都批准〕，到这段聊天结束为止有效。
    批准都只存在内存里。设置页只用来选听写方式，不触发发送，所以没有这个按钮。

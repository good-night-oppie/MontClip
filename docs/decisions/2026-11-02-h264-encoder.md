# ADR 2026-11-02: which encoder makes H.264 (MP4) exports

Status: decided by the owner on 2026-11-02 (relayed by Deja: 「按这个来（A + 可选本机
FFmpeg）」); implemented in PR #28 (draft). Not legal advice; the patent points below
should be confirmed by someone who knows software licensing before a public release.

## Context

MontClip runs only the FFmpeg it ships (`ffmpeg-path.js`), and ships only an LGPL
build (no GPL components: team rule, MIT project). The LGPL build has no libx264, so
without something else there is no software H.264 encoder: on a computer without a
usable graphics-card encoder, MP4 export failed (`Unknown encoder 'libx264'`).

## Options (Deja, `2026-11-02-MontClip-导出MP4编码器选择.md`)

| | Option | Quality | Licence / patents | What the user does |
|---|---|---|---|---|
| **A** | Windows' own encoder (`h264_mf`, Media Foundation) + graphics-card encoders (NVENC / Quick Sync / AMF) | graphics-card encoders good; `h264_mf` software MFT usable, a little softer than x264 at the same size | the encoder comes with Windows or the graphics driver; MontClip does not distribute it | nothing; Windows "N" editions need the Media Feature Pack |
| B | openh264 inside the packaged FFmpeg | weaker than x264 | Cisco only covers its own published binaries; a statically built copy is not covered → patent risk | nothing |
| C | download Cisco's openh264 on first export | as B | patents carried by Cisco | must go online once; breaks "offline by default"; the current FFmpeg cannot load it that way |
| D | a GPL FFmpeg with x264 in the package | best | GPL obligations; breaks the LGPL-only rule | nothing |

## Decision

**A, plus an optional local FFmpeg.**

1. H.264 export uses, in this order: a graphics-card encoder (NVENC, Quick Sync,
   AMF, VideoToolbox — the existing 2-frame probe decides which answer), then
   Windows' `h264_mf`. An encoder with a minimum frame size (NVENC: 145×49) gives
   way when the output is smaller.
2. In Settings (desktop) the user may choose an FFmpeg already on their computer
   that has libx264. When they have chosen one and it checks out, H.264 exports
   use its libx264 first: that is what they asked for. (Deja, 2026-11-02: a user who picks
   their own FFmpeg in Settings, and it passes the check, is asking for x264's picture
   quality, so it goes ahead of the graphics card.)
3. With no H.264 encoder at all, export refuses before rendering and says why in
   plain words; on Windows without Media Foundation (an "N" edition) it points to
   the Media Feature Pack. It never pretends an export succeeded.
4. The package contains only the LGPL build. MontClip does not distribute x264
   and downloads nothing.

Reasons: only LGPL in the package; no x264/openh264 distributed by MontClip; offline
by default; most streamers' computers have a graphics-card encoder; the rest get
Windows' encoder; those who want x264 can use their own FFmpeg.

## The local FFmpeg (rules)

- Only the absolute path the user picks in the main process's file dialog
  (`montclip:ffmpeg:choose`). Never PATH, never a guess, never a path from the page.
- Checked before use: `-version` and `-encoders` with argument arrays, no shell; it
  must list libx264. The main process stores `{version:1, path}` in
  `userData/external-ffmpeg.json`; the server reads it
  (`MONTCLIP_EXTERNAL_FFMPEG_SETTINGS`) and checks again whenever the setting or the
  file changes (`external-ffmpeg.js`).
- Used only to encode an H.264 export (libx264, including raw encoding profiles that
  use libx264). Preview, decoding, probing, proxies and every other export use the
  bundled FFmpeg.
- If the file disappears or the check fails, exports fall back to point 1 and the
  export notes / Settings say why.

## openh264: a release blocker, and our own build without it (Deja, 2026-11-02)

The pinned BtbN LGPL build links libopenh264 (`--enable-libopenh264`). MontClip never
selects that encoder, but its code ships inside `ffmpeg(.exe)`, which conflicts with
"do not distribute openh264". Decision: **it must go before any release.**

- **Never chosen, whatever the build lists** (QQ, 2026-11-02): `Delivery.NEVER_ENCODERS`
  holds `libopenh264`. Encoder selection filters it out even when a build offers it. A delivery
  spec asking for it gets another encoder and a note. A raw encoding profile naming it is
  refused before ffmpeg runs, and `ffmpegArgs` throws rather than build such a command.
  A future build that still links it therefore cannot make MontClip use it
  (`test/h264-guard.test.js`).

- **release-check fails, not warns** (`desktop/ffmpeg-audit.js`):
  - a bundled build that reports `--enable-libopenh264` or lists a `libopenh264` encoder;
  - a manifest that still points at a BtbN release;
  - a manifest that does not declare `openh264: false`.

  Until the new build replaces the manifest, release-check on this branch fails. That
  is intended.
- **No BtbN variant without it.** The release we pin (autobuild-2026-11-01-12-49)
  offers gpl / lgpl × static / shared × master / 8.1 / 9.0. Every variant builds
  `scripts.d/50-openh264.sh`, whose `ffbuild_enabled` returns 0 for all of them.
  Checked on 2026-11-02 through the GitHub API.
- **Our own build, reproducible, on GitHub's runners**:
  `.github/workflows/build-ffmpeg.yml`, started by hand or by pushing `ffmpeg-build/**`.
  Every input is pinned:
  1. **BtbN/FFmpeg-Builds** at `5ece62897c650b863c1ddda7b6964845344aef2d`, the commit of the
     release the manifest pins: its `build.sh` and packaging.
  2. **BtbN's build image for that commit, by digest** (win64 `sha256:3dc7a24e…`, linux64
     `sha256:dc3e1867…`). It holds the cross toolchain and every other library, already built, so
     those stay exactly as in the pinned release. Why this is that image: 5ece628 is BtbN's newest
     commit (2026-10-31 16:51Z); BtbN's push run 41222097386 for it built the images, created
     21:37Z; the scheduled run that made `autobuild-2026-11-01-12-49` reused them.
     **Why not build the image ourselves:** that needs ftp.gnu.org for the toolchain, and GitHub's
     runners could not reach it on 2026-11-02. Run 41391684826 failed fetching gmp, the same outage
     that kept libiconv's licence text from being fetched.
  3. **FFmpeg `d7643a0fe3f4f65516c302eba045ba884faed015`** (n9.0.2-42), the manifest's source.
     BtbN's `build.sh` clones the head of `release/9.0`, which is now 3 commits ahead, so the
     workflow checks the commit out and fails on any other.
  4. **Only openh264 switched off:** the image's configure line has `--enable-libopenh264`; the
     build turns exactly that into `--disable-libopenh264` and stops if it is still enabled.
     The openh264 library stays unused in the image.
  5. **Checks:** `desktop/ffmpeg-build/verify-build.cjs`, plus the artifact name must carry
     `n9.0.2-42-gd7643a0fe3`.
     - On Linux the verifier runs the binary's `-version` / `-encoders`.
     - For win64 it reads the embedded configure string and searches the .exe for
       `libopenh264` / `WelsCreateSVCEncoder`.
     - The build must show `--disable-libopenh264`, no openh264 encoder or entry point, and nothing GPL.
  6. **Kept** 90 days with their SHA-256 and a source record (BtbN commit, image digest, FFmpeg
     commit, the change).
- **Checked locally, without compiling** (C: keeps its free space):
  - the change applied to that commit's `build.sh`, then rendered as the container would run it, gives
    the checkout, the check and the flipped flag;
  - the verifier **rejects** today's BtbN builds: linux64 "the build links
    libopenh264"; win64 the same, plus "ffmpeg.exe contains libopenh264".
- **Next, in order:**
  1. Run the workflow (push a branch `ffmpeg-build/<name>`; `workflow_dispatch` works once the file is on
     main). Actions does run on this repository: the first CI runs came on 2026-11-02, after the
     trigger change. The earlier "Actions is off on this fork" explanation was wrong.
  2. Publish the two archives as a release of this repository.
  3. Point the manifest at them, with `openh264: false` and their SHA-256.

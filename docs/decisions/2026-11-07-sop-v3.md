## 第一部分 产品（照 0.13 原文）

第一部分照 0.13 的「产品北极星」「观察与最小验证」「团队铁律与外发边界」三节原文，不在这里重写；写入身份时用文末的「身份短版」。

外发口径以 0.13 为准：MontClip 是 AI 编辑器，可以联网，没有「默认不联网」的约定（主人 2026-11-04）。主播的内容发出去之前，每次都显示发什么、发给哪个网站，由主播决定；即使选了「都批准」或 Yolo，也照样显示。密钥只放在软件后台。助手不能自己新增联网路径；新增联网或外发路径，要单独写 ADR 并经过 QQ 安全核验。不在后台联网，也不自动上报。

隐私的说法统一用下面这段（QQ 2026-11-07 提出），替换各身份里旧的「主播信息只在本地处理」：主播的录像和弹幕默认在本机处理；只有主播自己打开的联网功能（她自己配置的 AI 服务、她自己选的云端听写等）才会按上面的规则发送，每次发送前先显示内容和目标网站。账号信息不外发；她配置的服务密钥只用于连接她自己选的那个服务，不进日志和报告；团队自己的密钥只用 1Password 引用。对外分享前先打码。新增任何联网或外发路径，都要单独写 ADR、经 QQ 核验，写明发什么、发给谁、主播能不能关掉。

## 第二部分 流程

### 1. 时限（替换 v2「卡点响应」里的阈值）
- **非草稿**：承接 1 小时、修复 3 小时、复审 2 小时、合并 6 小时。超时就报告。
- **草稿**：
  - 2 小时没有动静，提醒负责人三选一：继续（给出下次推送的时间）、转送审、关闭；
  - 3 小时交 Deja 决定改派还是关闭；
  - 24 小时由 Deja 确认后关闭，以后可以重新打开；
  - 草稿的 reportAt 不超过承接时间加 3 小时；
  - 安全、隐私、clean-room 类的草稿按非草稿计时。
- **长周期工作**（构建、渲染、全量测试、成片生成）：每 1–2 小时回报一次进度，哪怕只写「还在跑，预计 xx:xxZ」。赶不上时要在到期前说。
- **共享协调检查**：Review Inbox 督查每 5 分钟跑一次（主人 2026-11-06 指定），只在状态有变化时唤醒人，没变化不报。全团队只保留一个督查例行任务。

### 2. 送审格式（由 sop-pr-lint 强制检查）
- PR 正文第一行写「QQ 请审」（不加 @），第二行写「负责人：<伙伴名>」。负责人要写实际改代码的伙伴，不写共用账号。
- 正文还要有：
  - 改动；
  - 复现；
  - 测试：每一行写结果数字，或写「没跑」加原因；
  - 依赖：写「无」，或写 #编号加类型。
- 改了剪辑或导出代码，加一行「音画同步：」。改了联网或外发代码，加一行「外发：内容 / 接收方 / 能否关闭」。
- 例外写成「SOP 例外：<项目> — 原因 — 证据：<链接或消息号>」。只有 QQ 用 GoodNightOppie 在**当前 head** 上提交 review、并在正文里写一行「SOP 例外已核验：<项目>」，例外才算数。
- 改动 `.github/workflows/**` 或 `.github/actions/**` 的 PR 一律判「需要 QQ 核验」。要放行，QQ 要在当前 head 上写一行「SOP 例外已核验：工作流」。
- **检查的局限**：机器只能核对格式。GoodNightOppie 是共用审批账号，只能证明是团队审批账号做的。例外是否属实，要靠 QQ 在 review 里写清自己核了什么。
- 推送后读回 reviewRequests，确认里面有 GoodNightOppie。列增量一律用 `git log --first-parent <上次通过的 head>..<当前 head>`。
- QQ 的批准锁定在 commit_id 上，head 变了就失效。

### 3. 合并
- 两个仓库都用 GitHub 合并队列：QQ 把已批准的 PR 加进队列，队列把 PR 叠在最新 main 上跑必过检查，通过了才合入。作者不再手动反复合 main。
- 合并顺序由 Deja 定。Deja 1 小时没回复，就由 QQ 按默认规则代排：有依赖的按依赖；没有依赖的，先合已批准、改动小、冲突少的。安全、隐私、clean-room 有疑问的不代排。

### 4. 审查分两层
- **初审**：
  - 媒体、导出、音画同步类 → Rea；
  - 界面和助手类 → DD 或 VV，按原职责指定一个实际负责人；
  - 主播看得到的文字 → JJ 定稿。
- **终审**：QQ 负责安全、隐私、clean-room 和最终核验，并执行批准与合并。
- 初审和终审可以同时进行，不用等超时才分出去。只改纯文档或 CI、不到 200 行的 PR，可以直接给 QQ 审。初审结论写在 PR 上，并绑定完整 head。

### 5. 决定以 PR 上的书面记录为准
- 和某个 PR 有关的裁决、定稿、验收结论，都写在那个 PR 的评论里，绑定 head，这就是正式记录。伙伴消息只做通知，写明「去看哪条评论」。
- 跨多个 PR 的决定，写进 reference/ 或 docs/decisions/ 下的 ADR，或写进 SOP。
- 消息投递失败时，PR 上的书面记录照样有效。但仍要按 v2 记录阻塞并上报，不能把「写了评论」当作「对方已经收到」。

### 6. 同时在做的事有上限
- 每个伙伴同时最多负责 2 件实现类工作，审查和验收不算在内。
- 新活由 Deja 排队，其他伙伴不直接给实现者派活；备援表里规定的接手照常。
- 名额满了，新活进 Deja 的队列，写明排第几、预计什么时候开始。

## 身份短版（写入身份时用这一段替换原来的 SOP 段，共 12 条）

> MontClip SOP v3（2026-11-07）：
> 1. 北极星：让剪自己直播的主播下播后不用命令行，用更少的主动操作时间，从自己的录像得到第一条愿意发的切片；画质、音画同步、隐私和每一步的决定权都不打折，做不到的如实说。优先做导入、找高光、改头尾、剪掉不要的、同步导出和打码；沿用「先做不带弹幕的高光切片」。观察量：同一主播、可比的录像，从选文件夹到她确认导出第一条满意切片，算主动操作分钟数，记下卡住的步骤。基线要她同意记录，没测就直说。小样本只算个案；合成素材和真人素材分开；准确率只用有授权的标注素材。
> 2. 铁律：引用 skills/montclip-clip/SKILL.md 的铁律 1–6 原文。
> 3. 联网：MontClip 可以联网，没有默认不联网的约定。但不自行联网，必须由主播操作触发并同意；不在后台联网，也不自动上报。任何外发之前，先显示内容和目的地，由主播决定；选了「都批准」或 Yolo 也照样显示。密钥只放在软件后台。录像和弹幕默认在本机处理，只有主播自己打开的联网功能（她自配的 AI 服务、她自选的云端听写等）才按上面的规则发送；账号信息不外发；她配置的服务密钥只用于连接她自己选的那个服务，不进日志和报告；团队自己的密钥只用 1Password 引用；对外分享前先打码。对主播写「可能用于训练」，不写「不会被训练」。新增联网或外发路径，要单独写 ADR 并经 QQ 核验。不采集遥测。生成画面不在路线图里。对外（README、商品页、公告）不写“可以联网”，写“联网只发生在你自己打开的功能里，发之前先给你看”；不用“Yolo”“后台”这类内部词，写“选了‘这个聊天中都批准’也照样显示”；“不采集遥测”“不自动上报”要等 Rea 或 QQ 用代码或测试核过，才能写进对外文案。
> 4. 时限：非草稿承接 1 小时、修复 3 小时、复审 2 小时、合并 6 小时。草稿 2 小时提醒、3 小时交 Deja、24 小时经 Deja 确认后关闭。长周期工作每 1–2 小时报一次进度，赶不上要在到期前说。督查每 5 分钟一次，只在状态变化时唤醒。
> 5. 送审：第一行「QQ 请审」，第二行「负责人：<伙伴名>」；写明改动、复现、测试（写数字或「没跑」加原因）、依赖；按改动的文件补写音画同步和外发。例外只认 QQ 在当前 head 上写的「SOP 例外已核验：<项目>」；改动工作流的 PR 一律判需要 QQ 核验。推送后读回审查人；增量用 first-parent 列出；批准绑定 commit_id。
> 6. 合并：用 GitHub 合并队列，作者不手动反复合 main。合并顺序由 Deja 定，Deja 1 小时没回复由 QQ 代排。
> 7. 审查分两层：初审媒体类给 Rea，界面类给 DD 或 VV，文案由 JJ 定稿；终审是 QQ，负责安全、隐私、clean-room、批准与合并。初审和终审可以同时进行。
> 8. 决定以 PR 上的书面评论为准，绑定 head；伙伴消息只做通知。
> 9. 每人同时最多负责 2 件实现类工作，新活由 Deja 排队。
> 10. 备援：媒体问题交 Rea、QQ 兜底；界面问题交 DD/VV、QQ 兜底；文案交 JJ、Deja 兜底；SOP 和督查问题交 BB、QQ 兜底；规则集和需要主人授权的操作，由 QQ 向主人申请。
> 11. 新功能、产品取舍类的任务，补一句：真实痛点（没有例子就标「猜测」）→ 最小验证 → 采用或停止的条件。
> 12. v2 的职责、安全、隐私、clean-room、人工审批、消息送达规则全部保留。全文见 Deja 和 BB 的 SOP v3 文档，ADR 入库后改用正式指针。

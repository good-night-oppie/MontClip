## 背景

现行审片路径通过本机命令行工具 `agy` 把片段发给 Google Gemini。目的地主机名只来自文档，运行时核不了（`verified:false`），所以在主人确认之前整机都发不出去；V23 实测也一直挂起。

外接审片桥（europa 上，按主人授权受控外发）已经用 OpenRouter 的 `google/gemini-4-carbon` 跑过同段审片，回执里的上游服务商是 Google AI Studio。它暴露出一个必须处理的问题：**只发 `video_url` 时 `audio_tokens=0`，模型只收到了画面**（案例①，attempt-03）。另外发一条独立 `input_audio` WAV 后，`audio_tokens` 才不为 0（案例②，attempt-04/05/06）。

主人据此决定内嵌审片也改用 OpenRouter 的 carbon。这是一条**新的外发路径**：主机、密钥、请求格式、上游服务商都变了。

## 决定（提议）

### 1. 发什么

每次检查发一个 HTTPS 请求（`two_pass` 模式发两个，见第 6 条），内容只有三样：

| 部分 | 内容 | 上限 |
|---|---|---|
| 片段视频 `video_url` | 这一段时间线加最多 10 秒引入，渲染成重新压缩的小视频，以 `data:video/mp4;base64,…` 内联（不放网址、不上传到别处）。**小视频里不带音轨**（编码时去掉声音），声音只走下面一条路，这样「发不发声音」只有一个开关 | 片段 ≤30 秒，引入 ≤10 秒；视频 ≤3.2 MB（沿用 `VIDEO.perSend`） |
| 独立音轨 `input_audio` | **从同一次渲染解出的声音**，WAV（PCM 16-bit）。音频 t 秒就是小视频 t 秒，两者从 0 秒对齐、等长；不降噪、不改增益。**默认发**，主播可以在确认框里选「这次只发画面」，那时不发 WAV，结果按「只看了画面」处理（第 7 条） | 提议 48 kHz 立体声，和外接实测一致：40 秒 ≈ 7.7 MB（**待 QQ 定**，见待核验 4） |
| 提示词 `text` | 现行的固定标准、五问、固定要求，以及 `scope` 允许带的工程文字和审美笔记（规则不变）；另加一句「视频和音频从 0 秒对齐，先依据音频听写，不许用画面字幕代替听到的话」 | 工程文字 ≤6000 字符（不变） |

- 为什么必须另发音轨：案例①已经测到只发 `video_url` 时 `audio_tokens=0`。这只说明那一次没收到声音，**不能推广为所有 `video_url` 都不带声音**。不过内嵌审片要检查吞字、字幕对不上，声音是核心，所以每次都另发音轨，不赌 `video_url` 自带声音。
- 音轨和视频必须同源：从发出的那份小视频解出，不从原始素材另取。这样确认框里看到的、实际发出的、模型收到的是同一段声音。记录里存两者的 sha256 和时长。
- **不发**（和现行 ADR 相同）：原始素材文件、工程文件、文件名、路径、用户名、账号、观众昵称（除非出现在这一段画面里）、其他段落的画面和声音。
- **弹幕和昵称：** 不单独发弹幕文件、弹幕文字或观众昵称列表。但录屏画面里看得到的弹幕、昵称和账号会**随画面一起发出去**，读出来的声音里提到的名字也会随音轨发出去。确认框里写明这一句。这和主人 11-12 已接受的范围相同（QQ 6874674433「还不知道的」一段），换了目的地仍要在确认框里说清楚。
- 和外接实测的不同：外接发的是带声音的 mp4 加 WAV；这里提议 mp4 不带声音。这个组合没有实测过，由 V23 的合成夹具那一次验证（声音只在 WAV 里，模型能复述口令才算收到）。
- 请求里的其他设置：`model:"google/gemini-4-carbon"`（写死），`stream:false`，`provider:{order:["Google AI Studio"], allow_fallbacks:false, data_collection:"deny"}`（见第 2 条），以及固定的 `max_tokens`。**不带** `user`、`metadata` 之类能认出主播的字段。

### 2. 发给谁

- **主机：`openrouter.ai`**（`https://openrouter.ai/api/v1/chat/completions`）。和现行路径不同，这次是 MontClip 自己发起 HTTPS 连接，主机名写死在代码里，发送那一刻由我们自己的代码连接，**可以在运行时确定连的就是这个主机**。但按 QQ 的裁定，`DEST_CONFIRMED` 仍然只能由主人设置（见第 4 条）。
- **上游锁定（QQ 核验点 2）：** 模型 ID 写死 `google/gemini-4-carbon`；`provider.order` 只列 Google AI Studio，`allow_fallbacks:false`，`data_collection:"deny"`。这家不可用时请求直接失败（不重试，见第 6 条），不会转到别家。
- **上游以回执核对。** 外接三次实测（attempt-03/04/06）的回执都是 `provider: "Google AI Studio"`。每次检查的结果和本机记录里都写下回执中的 `model` 和 `provider`。**回执里的模型或上游和锁定的不一样，这次结果作废**（`no_result: PROVIDER_MISMATCH`，不显示模型说的话，字节照记）；**回执里没有 provider，记「上游未知」，结果也作废**，不猜。
- **这几项是否真被遵守，我们核不了。** `provider.order`、`allow_fallbacks`、`data_collection` 都是我们对 OpenRouter 的要求；OpenRouter 有没有照做、上游 Google AI Studio 有没有保留或拿去训练，我们只能看回执，看不到对方内部。界面和工具说明照这个意思写：「已要求对方只交给 Google AI Studio、不收集数据，是否遵守无法核实」，不写成「不会被用于训练」。

### 3. 主播的开关，和发送前怎么给主播看

- **主播的开关（QQ 核验点 3）：** 软件设置里新增一个开关，白话写作「审片时把片段发到网上的 AI 服务」（最终字句 JJ 定），**默认关**。只有主播自己在设置里打开；随时能关，关掉后正在准备的检查作废、不再发送，已经发出去的收不回（界面写明）。开关存在 Electron 主进程，页面和 Agent 都写不了（第 9 条）。没打开时 `prepare` 直接回 409 `REVIEW_SEND_OFF`，什么都不渲染。
- **第一次发送前的一句白话（PG）：** 主播第一次发送之前，先用一句白话告诉她发到哪里、发什么，例如「这 10 秒的画面和声音会发给网上的 AI 服务帮你检查」。这句里**不出现 OpenRouter、carbon、token** 这类词；秒数和「画面和声音 / 只有画面」按这次实际要发的填。最终字句由 JJ 定。服务名、域名、模型这些技术细节放在「查看详情」里，不放在这句白话里。
- **每次发送前都显示内容和目的地**，包括选了「都批准」和 Yolo 的时候。这和 `2026-11-03-agent-permission-modes.md` 一致：「都批准」只省掉点击，不省掉显示。显示的东西：
  - 发什么：片段起止、引入起止、总秒数；「带声音（另附一条独立音轨）」；会带的工程文字和审美笔记原文（`willSend` 规则不变）；视频和音轨各多少字节。
  - 发给谁：主文案用上面那种白话（「网上的 AI 服务」）；「查看详情」里写「OpenRouter（openrouter.ai），模型 google/gemini-4-carbon，指定交给 Google AI Studio；上次实际由 X 处理（以对方回执为准）」和「已要求对方只交给 Google AI Studio、不收集数据，是否遵守无法核实」。白话主文案加上可展开的详情，算不算满足 11-03「显示目的地」，**待 QQ 核验**（待核验 11）。
  - 发几次：「发 1 次」或「分 2 次发送」。
- 发送那一刻再核对一次目的地（主机、模型、`data_collection` 设置），和展示的不一致就 409 `DESTINATION_CHANGED`，什么都不发（沿用现行做法，核对项加上模型）。
- **11-12 的 Agent 例外不延伸到内嵌产品（QQ 核验点 3，第二版改）：**
  - 主人 11-12 的「Agent 审片不用点、不用显示」（QQ 6874674433）**只管开发侧的 Agent**，也就是团队自己的 Agent 通过 MCP 或 HTTP 调审片、服务进程上由主人打开 `MONTCLIP_REVIEW_AGENT_SEND`。它**不自动延伸到产品里给主播用的内嵌审片**。第一版把它写成「新目的地可以继承『不用点』」，这一版撤回。
  - **内嵌产品走 11-03 的规矩**（`2026-11-03-agent-permission-modes.md`）：每次发送前都显示内容和目的地；「都批准」和 Yolo 只省点击、不省显示；主播的开关没开，任何人都发不出去。
  - **待主人定：** 主播在产品里的 AI 助手（不是开发侧的 Agent）替主播发审片时，能不能像「都批准」那样省掉点击。主人定之前，按最严的做：每次都要主播点〔发送〕。
  - 开发侧的 `MONTCLIP_REVIEW_AGENT_SEND` 例外换到新目的地后是否还成立：也**待主人定**。主人定之前它对新目的地不起作用，开发侧的 Agent 只能准备（`prepare`），发不出去。

### 4. 目的地确认（DEST_CONFIRMED）

- 新路径只认 `MONTCLIP_REVIEW_DEST_CONFIRMED=openrouter.ai`，必须逐字相同。以前为 `daily-cloudcode-pa.googleapis.com` 设的值**不确认新目的地**。
- 只有主人能设置，在软件后台由主人亲自确认。Agent 不得设置或建议设置，MCP 和 HTTP 都没有写它的接口（照现行做法）。
- 没设置时 `prepare` 在渲染前就回 409 `DESTINATION_UNVERIFIED`（照现行做法）。
- 主人的「内嵌也用open router的 carbon」只定了**发到哪里**，不等于主人已经设置了 `DEST_CONFIRMED`，也不撤销正式 6 次的暂停。

### 5. 密钥

- **钥匙是谁的、费用谁付：待主人定（PG）。** 这是产品问题，ADR 答不了。参考数：外接 attempt-04（15 秒画面加独立音轨）回执里的费用约 0.024 美元，也就是每次检查大约 0.02 美元；`two_pass` 发两次，约翻倍。可选的做法比如主播自己配钥匙自己付，或者用团队的钥匙由团队付，各有不同的密钥保管和吊销问题，由主人定。**这一条不挡这次的同段实测**：同段实测用哪把钥匙，按现行规矩由主人定，团队的钥匙只用 1Password 引用。下面写的是「主播自己配」时的存法；换成团队的钥匙，存法和「不进日志、报告、记录」的要求不变。
- 主播自己配的情况下，OpenRouter 密钥**在软件后台配置**，存法和现有 AI 服务连接一样：Electron 主进程的 `safeStorage`（Windows 上是 DPAPI，绑定这个 Windows 用户）。加密不可用或只有 `basic_text` 时拒绝保存（`KEY_STORE_UNAVAILABLE`），不退回明文。
- 密钥**只在发请求的那一刻、在内存里**放进 `Authorization` 头。它不进：工程文件、`reviews/` 记录、服务器日志、子进程环境、MCP 和 HTTP 返回、报告、截图、PR、GitHub、测试夹具。测试用合成的假密钥哨兵，断言磁盘上任何文件、任何返回里都没有它。
- Agent 看不到、设不了、也不能「代填」密钥。页面也只能写入，读不回来。
- 团队测试用的密钥只用 1Password 引用，正文只写「OpenRouter key」（规矩见 `2026-11-04-openrouter-key-leak-incident.md`）。
- 和助手聊天用的 OpenRouter 连接共用一把钥匙，还是单独存一把：**待 QQ 核验**（待核验 5）。我建议单独存一把，费用和吊销互不影响。
- 发请求的进程：我建议由**持有密钥的 Electron 主进程**发出，引擎服务器只负责准备小样，不经手密钥（待核验 6）。这和现行的页面密钥设计一致：不是桌面应用启动的服务器发不出去。

### 6. 限制

- **不重试。** 任何失败（网络、超时、HTTP 非 200、回答格式不对）都结束这次检查，结果是 `no_result` 加原因，不自动再发。`two_pass` 的第一次失败了，就不发第二次。
- **失败和取消（QQ 核验点 7）：** 固定原因码，不带路径和对方原文：超时 `TIMEOUT`；401/403 `AUTH_FAILED`（界面提示主播去设置里检查密钥，不显示密钥）；429 `RATE_LIMITED`（只提示稍后再试，不排队、不自动再发）；其他 HTTP 非 200 `FAILED`；主播取消 `CANCELLED`。
- **不留半截上传：** 视频和音轨是内联在一个请求体里的，不走单独的文件上传接口，所以对方那边没有一个「已上传的文件」要我们去删。超时或取消时中止这条连接；本机的小视频、WAV、请求体缓存在 `finally` 里删除（照现行做法）。**对方收到一半的请求体会不会被留下，我们核不了**，界面上不写成「已撤回」。中止前已经发出的字节照样记账。
- 超时：提议 360 秒，和外接实测一致。
- 片段和引入沿用 30 秒 / 10 秒；每个工程累计上限沿用 **100 MB**，按**实际 HTTP 请求体字节**记账（base64 之后的字节，含视频、音轨和提示词）。按提议的音轨规格，一次最多约 11 MB 原始字节，base64 之后约 15 MB，100 MB 够 6 次左右；`two_pass` 按两次算。
- `DEST_CONFIRMED` 只能由主人设置（第 4 条）；主播的开关默认关（第 3 条）；开发侧 `AGENT_SEND` 对新目的地不起作用，待主人定（第 3 条）。
- 本机发送台账读不出来就不发（第 8 条）。
- 只接受本机连接、一次性发送令牌、发送内容在 `prepare` 时快照、渲染后工程改过就不发：都照现行做法。

### 7. 结果怎么用（六个案例里落到内嵌的四条）

案例出处：europa 上的 `montclip-eval/review-consistency-20261114/PRODUCT-CASES.md`（已读到，2026-11-14 版）。任务里说的 `documents/2026-11-14-外接与内嵌审片交替推进-需求案例.md`：**未读到**（europa 主目录下没有 `documents/` 目录），所以下文只按 PRODUCT-CASES.md 写。

给主播看的只有三种白话状态（PG 6878569226）：「建议你改这里」「这里请你确认」「声音没检查」。**哪一种都不自动改片子**，也不触发重剪。文案由 JJ 定稿。离线红测在分支 `deja/321-review-redtests`（#321 6879018542；C7、C8 按 PG 6878593931 更新，见本节下文）。

- **案例①「声音没检查」（QQ 核验点 6）：** 请求带了 `input_audio`，但回执 `usage.prompt_tokens_details.audio_tokens` 是 0 或没有这个字段；或者主播选了「这次只发画面」。这时结果标「声音没检查」，记录里写 `audioVerified:false`、`inputs:["video_url","text"]` 或实际收到的情况。**界面和记录都不能说「听过声音」，要如实写成只看了画面。** `subtitle` 和吞字这类靠声音的结论**不能算通过**，最多算 `insufficient_evidence`，整次检查不能是 `passed`。反过来，`audio_tokens` 不为 0 只说明模型收到了声音，**不等于听懂了**，也不是人工真值。
- **案例③ 漏字幕：** 模型说某处有句话字幕里没有，显示成带时间点的「建议你改这里」，主播点确认才改。
- **案例⑤④ 不确定只提示，合成一条：** 画面文字几次读得不一样、换屏时间和说话对不上，都只显示「这里请你确认」，不给替换字，不挪时间。模型给的时间点不当切点；模型时标和本机 ASR 的小数秒都不是精确真值。
- **C7 先和实际帧核对，矛盾就不显示（PG 6878593931）：** 模型对画面的说法（换屏时刻、画面上的字），先和本机从发出去的那份小视频解出的实际帧核对。和实际帧矛盾（例如实际帧 11.4 秒才换屏，模型说 11.0 秒已换；实际帧上是「甲」，模型读成「乙」），这条说法**压下来，不显示**，连「这里请你确认」也不出，不生成修改，不触发重剪。和实际帧一致的说法照常显示，最多是「这里请你确认」。本机核对只用本机解出的帧，不再外发任何东西。
- **C8 只有画面文字一个依据时，最多「这里请你确认」（PG 6878593931）：** 本机没有那一处的帧上文字可核对、模型又只凭画面文字说话时，最多显示「这里请你确认」，不能显示「建议你改这里」，也不给替换字。「建议你改这里」只留给 ③ 这一类：声音里有、字幕里没有。
- **案例⑥ 片段之外不下结论：** 结果写清审了哪一段（`reviewed`）。只对实际发出去的片段下结论；关于片段外的发现丢掉，不提片段外的切点。片段边界截断的话不判成全片切点错误。
- 案例②：听写只作建议的依据，不单独进字幕。

### 8. 本机记录

`reviews/<工程>.json` 照现行规则：只存结构化字段，原话和密钥不落盘。新增以下字段：

- 目的地：`{host:"openrouter.ai", model, dataCollection:"deny"}`。
- 回执：`model`、`provider`（没有就是 `null`，显示「上游未知」）、生成 id、`usage` 里的数字（prompt、completion、audio、video tokens）、费用数字。
- 发了什么：每一遍发了哪几类（`text`、`video_url`、`input_audio`）、各多少字节、视频和音轨的 sha256、时长、发起人（主播或 Agent）、时间。
- `audioVerified`。
- 不存：提示词原文、模型回答原文、密钥、请求头。
- **发送台账照 #339 的口径（QQ 核验点 5）：** 已发字节数单独累计（`sentBytesTotal` 加进程内存下限，`sentTotal` 取两者较大者），按实际请求体字节记，写记录失败或旧记录被滚掉都不让总量变小。**发送前先读台账；台账读不出来（不是「还没有台账」）就不发**，这次检查标为失败、删掉小样，原因码 `LEDGER_UNREADABLE`，一个请求都不发。还没有台账只是第一次发送，照常。#339 还没合并；本路径的实现 PR 在 #339 合并之后做，直接用它的 `countSent` / `sentTotal`。

### 9. 不给 Agent 留口子

- `MONTCLIP_REVIEW_DEST_CONFIRMED` 和 `MONTCLIP_REVIEW_AGENT_SEND` 是服务进程的环境变量，照现行做法：MCP、HTTP、页面都没有写它们的接口，工具说明里写明 Agent 不得设置或建议设置；CLAUDE.md 里这条保留。
- 本 ADR 新增的三样也一样：主播的开关、OpenRouter 密钥、目的地确认，都只存在 Electron 主进程，只能在设置窗口里由人操作写入。不加任何 MCP 工具、HTTP 路由或页面接口去改它们。
- 实现 PR 要带反向测试：列出所有 MCP 工具和 HTTP 路由，断言没有一个能写这几项；用 Agent 身份调 `send` 在开关没开、目的地没确认时分别回 `REVIEW_SEND_OFF`、`DESTINATION_UNVERIFIED`，一个请求都不发。

### 10. 新依赖

**没有。** 请求用 Node 自带的 `https`（或内置 `fetch`）发；WAV 用已经打包的 FFmpeg 从同一次渲染里解出；JSON 和 base64 都是内置的。不加 npm 包，不加新的二进制，不需要新的许可证条目。实现时如果发现非加不可，先停下来报主人授权，并写清许可证。

### 11. 外接的结果不能抵内嵌的同段实测（PG）

外接审片桥和内嵌审片现在用的是同一家服务、同一个模型，但外接的结果**仍然不能代替**内嵌的同段实测。两边不一样的地方：

- **请求的写法：** 外接是团队手写的脚本，内嵌是产品代码拼的请求；字段、提示词、`provider` 设置、视频带不带声音（第 1 条提议内嵌的视频不带声音，外接带）都可能不同。
- **音轨的抽法：** 外接从成片 mp4 抽出 WAV；内嵌从同一次渲染里解出，采样率、声道、长度的处理可能不同。
- **结果的解析：** 外接的回答由人读；内嵌的回答要过 `parseVerdict`，按三种状态、C7 帧核对、C8、片段外丢弃来处理。

案例①就是例子：同一个模型，换一种写法（只发 `video_url`），声音就没送到。所以内嵌要用它自己的代码，在同一段上真发一次（V23），看声音有没有送到、结果怎么显示；外接的成功只能当需求和参照，不能写成内嵌已经验证过。

## 原来的目的地和 #326 怎么处理（建议，由 QQ 和主人定）

- **`agy` 路径：建议替换，不并存。** 理由：两条外发路径并存，确认框要说清楚这次发往哪条，开关、记账和 `DEST_CONFIRMED` 也要分两套，外发面积翻倍；而且 `agy` 路径到现在一次都没真实发出过，没有可沿用的实测。实现 PR 里把内嵌发送路径的发送端换成 OpenRouter；`agy` 相关代码是删掉，还是留着但永远不可达，由 QQ 定。`DEST_CONFIRMED` 只认 `openrouter.ai`。

## 后果

- 好处：主机由我们自己的代码连接，运行时可以确定；回执给出模型、上游和音视频 token 数，「是否收到声音」第一次可以量化；不再依赖本机装 `agy`、登录 Google 账号。
- 代价：要有人配一把 OpenRouter 密钥并付费用（每次约 0.02 美元；是主播还是团队，待主人定）；多了一个中间方（OpenRouter），上游由它选择，`data_collection` 只能要求、不能核实；独立音轨让每次的请求变大，100 MB 能用的次数变少。
- 不变：外发前给主播看内容和目的地、发出去的就是展示过的、原话不落盘、模型的话只是数据、`passed` 只由检查本身产生。
